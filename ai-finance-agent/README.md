# AI + 金融 Agent 应用开发调研

> 调研日期：2026-11-12
> 资料范围：金融监管机构与央行报告、咨询机构行业研究、主流 Agent 工程实践文档、同行评审/预印本论文。所有引用在文末及 [`04-参考来源.md`](04-参考来源.md) 中列出来源与链接。

## 一句话结论

金融 Agent 的价值不在“更会聊天”，而在于把**文档密集、数据密集、强合规**的业务流程拆成**边界清晰、工具可调用、结论可引用、错误可回滚、关键节点有人审**的工作流。提效最大的不是“全能员工”，而是“**带工具的初级分析师 + 永远在线的审核员**”；技术投入的优先级大致是：**RAG 与工具/上下文工程 ≈ 评测与治理 > 记忆 > 多 Agent 编排 > Prompt 技巧**。

## 核心判断（先看这五条）

1. **金融的高价值 Agent 首先是“证据机器”，不是“答案机器”。** 每个结论要能追溯到原文、数据版本和计算过程；否则在投研、信贷、合规场景不可用。
2. **“人在环”不是过渡方案，而是产品设计。** 英国央行与 FCA 2024 年联合调查显示，55% 的 AI 用例存在某种程度的自动决策，其中 24% 为半自主（关键或模糊决策保留人工监督），仅 2% 为完全自主决策。[3] 监管报告也反复强调模型风险、数据质量与治理责任仍由金融机构承担。[1][2]
3. **工具调用比“更长的提示词”更能提升正确率。** 金融计算、行情、账户、额度、对账都应交给确定性工具；LLM 负责理解、规划、解释与生成，不负责心算。
4. **研发提效的证据是分化的。** GitHub Copilot 的受控实验显示任务完成快 55.8%[19]；但 METR 2025 年对资深开源开发者的随机对照试验发现，在其熟悉的成熟仓库中允许使用 AI 工具反而慢 19%[20]。结论不是“AI 无用”，而是**任务边界、测试完备度、代码库熟悉度决定收益**。
5. **多 Agent 不是默认答案。** 先把单 Agent + 工具 + 工作流做扎实；只有在任务可分解、可并行、工具/权限确需隔离时，再引入多 Agent，否则调试成本和错误传播会吃掉收益。[10][11]

## 调研方法与边界

- 优先采用**监管机构、央行、国际组织**的一手文件（FSB、IMF、英国央行/FCA、欧盟、NIST），其次为咨询机构与厂商工程文档，最后用论文补充具体技术结论。
- 对厂商/咨询案例（如某银行法务 Agent 的 92.9% 准确率）保留“来源方自述”限定，不作为独立基准。
- 本调研是**公开资料综述**，不构成投资建议、法律意见或合规认证；具体落地需结合所在司法辖区的监管要求与机构自身模型风险管理流程。
- 文中数据均标注来源；引用编号对应 [`04-参考来源.md`](04-参考来源.md)。
